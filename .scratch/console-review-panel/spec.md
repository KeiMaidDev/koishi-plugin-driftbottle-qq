# Spec: 漂流瓶控制台管理面板

Status: ready-for-agent

> 术语（瓶子、留言、封禁、举报、待处理举报、忽略举报、管理员）以仓库根 `CONTEXT.md` 术语表为准。

## Problem Statement

管理员目前只能通过 QQ 私聊通知和指令（封漂流瓶/解漂流瓶/删留言）对瓶子做事后管理：看不到全貌，举报没有可视化闭环，被举报后是否处理、被谁处理无从追踪；图片内容要靠 QQ 端消息逐个查看，效率低。

## Solution

在 Koishi 控制台内嵌一个漂流瓶管理面板：管理员登录控制台即可浏览所有本地瓶（含留言），对被举报的瓶子做封禁/忽略举报，对留言做删除；新举报实时推送到面板；操作写入与指令一致的日志。仅管理本地瓶，云瓶不在范围内。

## User Stories

1. As a 管理员, I want to 在 Koishi 控制台打开漂流瓶管理面板, so that 我不必在 QQ 客户端里逐条处理审核事务
2. As a 管理员, I want to 看到瓶子列表（ID、作者、文字摘要、状态徽标）, so that 我能快速总览海里的瓶子
3. As a 管理员, I want to 按「全部 / 被举报 / 已封禁」筛选瓶子, so that 我能聚焦需要处理的内容
4. As a 管理员, I want to 被举报的瓶子按举报数降序排在前面, so that 举报最多的瓶子最先被我看到
5. As a 管理员, I want to 看到所有有举报的瓶子（哪怕只有 1 人举报）, so that 低举报数的真实问题不被阈值埋没
6. As a 管理员, I want to 看到顶部统计条（瓶子总数、正常/封禁数、待处理举报数）, so that 我第一眼就知道有没有事要处理
7. As a 管理员, I want to 待处理举报按「举报数达到阈值且未处理」口径统计, so that 统计条与 QQ 通知口径一致
8. As a 管理员, I want to 按瓶子 ID 或作者 ID 搜索, so that 我能直接定位用户报过来的某个瓶子
9. As a 管理员, I want to 瓶子列表分页且分页在后端切片, so that 瓶子积累几千条时页面依然流畅
10. As a 管理员, I want to 点击列表行查看瓶子详情（完整内容、图片、音频、全部留言）, so that 我能基于完整信息做判断
11. As a 管理员, I want to 在详情页内联预览瓶子和留言的图片, so that 我不用去 QQ 端看图就能判断内容是否违规
12. As a 管理员, I want to 在详情页播放音频, so that 语音瓶子我也能审核
13. As a 管理员, I want to 看到已软删除的留言并带「已删除」徽标, so that 我能看到谁删过什么的全貌
14. As a 管理员, I want to 封禁瓶子, so that 违规内容不再对普通用户可见
15. As a 管理员, I want to 解封瓶子, so that 误封的内容可以恢复
16. As a 管理员, I want to 删除留言（软删除）, so that 评论区的违规内容被清理
17. As a 管理员, I want to 忽略举报, so that 误报的瓶子不封禁、举报记录也闭环不再催办
18. As a 管理员, I want to 封禁或忽略举报后该瓶举报标记为已处理, so that 同一个瓶子不被重复通知
19. As a 管理员, I want to QQ 端审核通知按钮对已处理的瓶子提示「已处理」, so that 网页和 QQ 两条处理入口不打架
20. As a 管理员, I want to 危险操作前有确认弹窗, so that 我不会手滑封错瓶子
21. As a 管理员, I want to 网页操作写入与指令相同的日志、操作者记为 console(用户名), so that 日志里能区分并追责网页操作
22. As a 管理员, I want to 新举报到达时面板通过 WebSocket 实时刷新, so that 我不用手动刷新就能看到新的待处理举报
23. As a 管理员, I want to 网页操作后列表即时反映状态变化, so that 我看到的状态永远是当前的
24. As a 管理员, I want to 只要登录了控制台就能使用面板（不要求在 adminQQ 白名单内）, so that 控制台操作员不需要额外配置就能审核
25. As a QQ 用户, I want to 我举报后管理员能更快看到并处理, so that 违规内容被及时清理
26. As a QQ 用户, I want to 被封禁的瓶子对我不可见、解封后恢复, so that 行为与现有指令完全一致

## Implementation Decisions

- **定位**：综合管理面板（事后审核），不是发布前审核；仅管理本地瓶。
- **权限**：面板及全部 API 只依赖控制台登录鉴权，不校验 `config.adminQQ`；adminQQ 继续只管 QQ 端指令。
- **控制台接线**：插件新增控制台扩展——声明 console 相关依赖，新建 client 目录（Vue），注册 `ctx.console` 服务与 API 路由，并在包元信息中声明 client 资源（koishi.public）。此前插件完全没有控制台扩展，全部从零搭建。
- **数据源**：沿用现有 LocalStorage 存储与内存数据结构，不新增数据库表；瓶子状态位 `show` 即封禁语义；留言沿用软删除标记。
- **API 服务模块**：面板后端收敛为一个服务模块，接口大致为 listBottles（分页/筛选/搜索）、getBottle、ban、unban、deleteReview、dismissReport、getStats。筛选维度为全部/被举报/已封禁，被举报按举报数降序；搜索按瓶子 ID/作者 ID；分页由 API 层对全量内存数据切片（后端分页）。
- **举报可见性口径**：被举报标签列出所有有举报的瓶子（含低于阈值的）；统计条「待处理举报数」按达到 reportThreshold 且未处理的口径。
- **举报闭环**：封禁或忽略举报后，该瓶举报记录标记已处理、清除通知进行中标记、不再重复 QQ 通知；QQ 端通知键盘按钮对已处理瓶子提示「已处理」。
- **新增能力边界**：忽略举报是本次新增的操作（现有指令没有对应物）；不新增「彻底删除瓶子」。
- **日志一致性**：网页操作复用现有日志类型与日志文件，操作者身份记为 console(控制台用户名)，与 QQ 端指令日志可区分。
- **媒体路由**：新增控制台路由把本地图片/音频流出去，带控制台鉴权与路径防穿越；file:// 路径按现有路径修正逻辑的 basename 规则解析。
- **实时性**：WebSocket 广播（新举报、数据变更事件），前端收到后重新拉取列表。
- **操作交互**：封禁/解封、删留言、忽略举报均带确认弹窗；操作语义与对应 QQ 端指令一致。

## Testing Decisions

- 只测外部行为：从 API 服务模块的公开接口断言返回数据与状态变化（show 位翻转、留言软删、举报闭环标记、日志条目），不断言内部实现细节。
- 唯一接缝：控制台 API 服务模块（listBottles/getBottle/ban/unban/deleteReview/dismissReport/getStats）。分页切片、筛选排序、待处理举报口径、忽略举报闭环、日志写入全部在这一接缝后验证。
- 测试形式沿用现有先例：纯函数 + 夹具数据（构造若干瓶子/举报记录 JSON），不启动 Koishi 应用、不需要 bot 适配器——与现有 message 测试同风格。
- 媒体路由与 WebSocket 广播是薄胶水层，不写自动化测试，靠手测验证；Vue 前端不在自动化测试范围内。

## Out of Scope

- 云瓶的任何管理（数据在远端服务器，本地无管理 API）
- 发布前审核（投稿待审→通过/拒绝）及相应数据模型变更
- 彻底删除瓶子
- QQ 端指令的行为变更（现有指令保持原样，仅「已处理」提示为闭环所需的最小改动）
- Koishi authority 权限体系接入
