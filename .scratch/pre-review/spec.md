# Spec：自动审核不可用时启用人工预审

Status: ready-for-agent

> 产出自 2026-09-05 的 grill-with-docs 访谈，全部决策经用户逐条确认。
> 决策背景见 [ADR 0001](../../docs/adr/0001-自动审核不可用时启用人工预审.md)，术语见根 [CONTEXT.md](../../CONTEXT.md)「预审」小节。

## Problem Statement

站点关闭了腾讯云不良内容审核（`isExamine`，或开了但 Appid/key 缺失导致实际不生效）时，用户扔出的瓶子不做任何检查、创建即入海，任何人捞到都能看到。管理员失去了把关入口——"关闭自动审核"变成了"完全无人把关"。

## Solution

当自动内容安全审核**实际不可用**时，用户扔出的瓶子不再直接入海，而是成为一份**待审投稿**：作者收到待审回执并可撤回；管理员通过 QQ 私信、QQ 指令或控制台面板对投稿做**预审**——**通过**后投稿转正为瓶子入海，**驳回**则丢弃投稿及其媒体文件。自动审核可用时，行为与现在完全一致。

## User Stories

### 作者（普通用户）

1. As a 普通用户, I want 在自动审核未生效时扔出的内容先由管理员过目，so that 海里的瓶子都是经过把关的、我不会误捞到不良内容。
2. As a 扔瓶作者, I want 提交后立即收到"已提交、等待管理员预审"的回执（不含瓶子 ID），so that 我知道瓶子没有消失，也没有被悄悄拒绝。
3. As a 扔瓶作者, I want 待审回执下有一个撤回按钮，so that 我反悔时一键进入撤回流程，不用记指令。
4. As a 扔瓶作者, I want 提交时自己决定"预审结果出来后是否私信推送给我"（默认不推送），so that 想收到结果通知的人能收到，不想被打扰的人不被打扰。
5. As a 扔瓶作者, I want 用 `漂流瓶/撤回投稿` 列出我名下的待审投稿（待审编号 + 内容摘要）并选择编号撤回，so that 我不记得编号时也能撤回。
6. As a 扔瓶作者, I want 撤回后投稿和配图/音频被彻底丢弃，so that 我的内容不会残留在服务器上。
7. As a 扔瓶作者, I want 撤回已被管理员处理过的投稿时收到"已处理，无法撤回"提示，so that 我不会误以为撤回成功了。
8. As a 扔瓶作者, I want 我的投稿被通过后收到个人日志（含新瓶子 ID），so that 我知道瓶子已入海、ID 是多少。
9. As a 扔瓶作者, I want 我的投稿被驳回后收到个人日志，若有驳回理由则一并展示，so that 我知道没过审以及原因。
10. As a 订阅了结果推送的作者, I want 预审出结果时收到一条私信（含驳回理由），so that 我不用反复来问。
11. As a 扔瓶作者, I want 待审投稿不被别人捞到、不出现在海里统计中，so that 未经把关的内容不会流通，统计反映的是真实入海生态。
12. As a 扔瓶作者, I want 我的待审投稿不会被批量上传到云海，so that 未过审的内容不会流向更远的服务器。

### 管理员（QQ 端）

13. As a 管理员, I want 有新的待审投稿时收到主动私信（含待审编号与内容摘要），so that 我不必盯着面板也能及时处理。
14. As a 管理员, I want 用 `漂流瓶/通过投稿 <待审编号>` 放行投稿，so that 好内容尽快入海。
15. As a 管理员, I want 用 `漂流瓶/驳回投稿 <待审编号>` 拒绝投稿，so that 不良内容到不了任何用户手里。
16. As a 管理员, I want 驳回时固定进入一轮理由输入，可用"跳过理由"按钮留空，so that 想说明原因时能说明，赶时间时也不被流程卡住。
17. As a 管理员, I want 待审编号全局递增且永不复用，so that 私信里提到的编号过几天仍指向同一份投稿。
18. As a 管理员, I want 处理一份已不存在的投稿（被撤回/已处理）时得到明确提示，so that 我知道操作没有生效及原因。
19. As a 管理员, I want 自己扔瓶不走预审，so that 不用在"给自己点通过"上浪费一轮操作。

### 管理员（控制台面板）

20. As a 控制台管理员, I want 面板上有待审列表（投稿内容与摘要），so that 我在网页上集中处理，不必翻聊天记录。
21. As a 控制台管理员, I want 每份待审投稿带"通过 / 驳回"按钮，so that 一键完成预审。
22. As a 控制台管理员, I want 面板驳回时弹出可留空的理由输入框，so that 网页端也能附上理由。
23. As a 控制台管理员, I want 面板操作后 QQ 端与面板数据双向刷新，so that 两个入口看到的状态始终一致。

### 维护者

24. As a 插件维护者, I want 预审的触发条件与自动审核的实际放行条件一致（配置开启但密钥缺失也算不可用），so that 不存在两条路径都放行的漏洞。
25. As a 插件维护者, I want 待审区存活于机器人重启之后，so that 积压的投稿不会因为重启而凭空消失或凭空入海。
26. As a 插件维护者, I want 待审投稿无自动过期，so that 删媒体文件的破坏性操作永远不会被定时任务自动执行。

## Implementation Decisions

以下决策均在访谈中经用户确认；术语以 CONTEXT.md 为准（预审 / 待审投稿 / 通过 / 驳回 / 撤回 / 待审编号；「审核」仍专指事后管理，「封禁」针对已入海的瓶子且不删除）。

- **触发判定**：预审在自动内容安全审核**实际不可用**时启用——`isExamine` 为 false，或开启但 Appid/key 缺失。判定函数为纯函数，与现有自动审核的放行条件互为补集；判定结果改变扔瓶流程走向，不改变捞瓶、留言等流程。
- **范围**：仅本地「扔漂流瓶」。留言、云瓶（含扔云漂流瓶）不预审。adminQQ 用户扔瓶跳过预审。
- **待审区存储**：独立新增一个存储模块（与现有举报注册表同构的注册表模式），使用独立的 LocalStorage 命名空间（与瓶子数据、历史记录命名空间平级），活过重启。**批量上传云漂流瓶不得读取或包含待审区内容**——独立存储天然隔离，实现时不得合并读取。
- **待审投稿模型**：待审投稿不是瓶子：不入瓶子库、不占瓶子 ID、捞不到、不计入海里统计（统计不改动）。瓶子 ID 在通过时才分配并递增。
- **待审编号**：全局递增计数器，随待审区持久化，只增不复用；管理员通知、通过、驳回、撤回均以待审编号指代投稿。
- **生命周期**：提交→待审区（媒体文件此时即下载到本地媒体目录）；通过→转正为瓶子（分配 ID、入海、复用现有发布日志）；驳回→删除投稿记录与已下载的媒体文件；撤回→与驳回同效。无自动过期。
- **作者侧交互**：提交成功回执不含瓶子 ID，回执下附撤回按钮（复用现有引导按钮机制）；提交流程中附带"结果是否私信推送"选择，默认否，偏好随待审记录保存。新指令 `漂流瓶/撤回投稿`：不带参数列出本人待审投稿并 prompt 选编号，交互对齐现有「删留言」；已被处理的投稿提示无法撤回。
- **管理员侧交互**：待审产生时复用现有主动私信通道通知 adminQQ（含待审编号与摘要）；新指令 `漂流瓶/通过投稿 <待审编号>`、`漂流瓶/驳回投稿 <待审编号>`；驳回固定进入一轮理由 prompt，可跳过（带"跳过理由"按钮），理由可留空；指令命名用「投稿」而非「瓶子」。
- **控制台面板**：新增待审列表区块，每份投稿附通过/驳回按钮，驳回弹出可留空的理由输入框；操作后复用现有面板变更广播，QQ 端与面板双向刷新。面板权限维持现状（控制台登录本身，不要求在 adminQQ 内）。
- **通知与日志**：通过/驳回写作者个人日志（扩展现有日志类型；驳回理由仅出现在作者日志与订阅推送中，不公开）。撤回不通知管理员——管理员处理时自然收到"投稿不存在"提示。
- **文案与按钮值**：所有新增用户可见文案、回执、按钮走现有消息构造模块，保持 QQ markdown 兼容处理不变。

## Testing Decisions

- 好的测试只测外部行为（给定输入与存储初态，断言返回值与持久化结果），不测内部实现细节；断言文案只断言关键语义（如回执不含瓶子 ID、驳回理由出现在作者侧输出），不逐字比对。
- **新增唯一接缝**：待审区注册表模块。用假 LocalStorage（与举报注册表现有测试相同的注入方式）直接测试：提交分配待审编号、编号不复用、通过转正语义（返回供落库的数据、编号作废）、驳回/撤回清理记录与媒体、重启后（用同一存储重建注册表）编号计数与待审列表完整、撤回已处理投稿返回失败。**「自动审核实际不可用」判定函数**作为该模块的纯函数一同测试（isExamine 开/关 × 密钥有无的真值表）。
- **复用接缝一（消息构造）**：新增回执、按钮值、管理员通知、撤回列表等构造函数，按现有消息构造测试的模式测试（重点：QQ 端 markdown 兼容、按钮值约定）。
- **复用接缝二（ConsoleService）**：面板的待审列表与通过/驳回动作，按现有 ConsoleService 依赖注入测试的模式测试（注入待审注册表假实例与瓶子数据，断言动作结果与变更广播）。
- QQ 指令在主入口的接线不建测试接缝（与现有代码库做法一致，现有指令层同样无测试）。

## Out of Scope

- 留言预审、云瓶预审（扔云漂流瓶的内容由远端服务器管理，本插件无权限）。
- 作者撤回或删除**已入海**的瓶子（封禁仍走现有事后管理）。
- 待审投稿自动过期、定时清理。
- 驳回强制填写理由。
- 管理员撤回通知、作者撤回已处理投稿的补救。
- 海里统计口径的任何改动（待审投稿不计入）。
- 自动审核可用时的任何行为变化。

## Further Notes

- 本 spec 是行为变更：旧版本"关闭审核 = 完全放行"，新版本"关闭审核 = 人工预审兜底"；依赖旧行为的部署者需在升级说明中知晓。
- 待审区堆积是可见的运维信号，控制台面板应暴露待审数量，方便维护者发现管理员长期未处理。
- 实现时相关架构约定（无 strict tsconfig、事件类型扩展位置等）见控制台审核面板的既有实践。
